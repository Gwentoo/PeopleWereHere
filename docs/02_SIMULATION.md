# 02 — Модель симуляции

> Технические требования к вычислительному ядру. Начальные коэффициенты — **гипотезы**, настраиваемые в файлах конфигурации; никаких обязательных открытий «к определённому году».

## 1. API чистого ядра

Задача архитектуры — один и тот же движок для браузера и headless-тестов.

Пример предполагаемого интерфейса (имена можно изменить):

```go
// Init(seed, opts) создаёт партию и детерминированный RNG.
// Apply(command) валидирует команду относительно state и принимает/отклоняет её.
// Step(state, rng, rules) продвигает мир ровно на один игровой день.
// Snapshot(state) даёт безопасный для клиента DTO.
// RunUntil(state, policy, maxDays) запускает headless-партию.
```

- Функция `Step` **не читает** часы ОС, файлы, HTTP и не спит; не обращается к глобальному генератору случайных чисел.
- У движка единый последовательный порядок изменения состояния, без гонок и непредсказуемой асинхронности.
- Реальный таймер в transport-слое преобразует прошедшее время в количество `Step`. При быстрой перемотке всё равно выполняются проверки промежуточных дней.
- Каждый игровой день выполняется по стабильному порядку (обсуждаемая реализация):
  1. Проверка окончания игры/блокировки важным решением.
  2. Выполнение уже принятых команд и завершение задач со сроком на сегодня.
  3. Обновление производства/пищи/сока и населения.
  4. Развитие знаний, исследований, институтов и автономных инициатив.
  5. Обработка активных долгосрочных процессов и условий событий.
  6. Случайные проверки нового контента по установленным условиям.
  7. Старение, травмы/здоровье и смерть героя/NPC.
  8. Запись произошедших событий в историю и клиентскую очередь.
- Допустимо изменить порядок, но зафиксировать его тестами и **не допускать изменения из-за порядка обхода map в Go** (сортировать ключи там, где важен RNG).

## 2. Структура состояния партии (логическая)

| Сущность | Содержимое |
|---|---|
| `GameMeta` | ID, seed, версия правил/контента, игровой день, дата начала, режим/статус, RNG state |
| `Player` | возраст в днях, характеристики 0–10, здоровье/условия, жив, ограничения личного участия |
| `World` | регион и биом, континенты/водные барьеры, известность областей, список значимых объектов |
| `Population` | численность, статистика широких навыков/возраста, агрегированные рабочие группы, важные NPC |
| `Revival` | деревья и их фиксированные скорости, найденные пригодные статуи, накопленный сок, ёмкость хранилищ |
| `Economy` | обобщённая пища/обеспечение, производственный потенциал, рабочие силы, благополучие |
| `Science` | технологии: знание/прогресс/практическая доступность, озарения, приоритеты, сохранённые записи |
| `Culture` | доступные институты, действующие институты, общественные тенденции, длительные культурные процессы |
| `Tasks` | активные личные и коллективные задачи с остатком времени, статусом и причинами невозможности |
| `Events` | активные процессы, cooldown, ожидаемые решения, лента, журнал памятных событий |
| `Settlements` | ID, имя, дата основания, примерное население, специализация и ключевые события |

Хранить **stable ID**, а не связывать сущности по имени или по индексу массива. NPC-ссылка переживает переименование и смерть. Состояние игрока не должно включать скрытые факты, выдаваемые клиенту до их открытия.

## 3. Детерминированная случайность

- Один seed при создании мира. Один локальный RNG, принадлежащий `GameState`, или отдельные **документированные** seed-потоки для генерации мира/людей/событий, чтобы разные модули не сбивали друг другу результаты.
- Требуемый результат: **одинаковая версия игры + seed + одинаковая последовательность команд с игровыми датами** → одинаковое состояние, события и исход.
- Для сохранений сохранять внутреннее состояние RNG или обеспечивать эквивалентное восстановление; просто хранить seed недостаточно для продолжения партии с середины.
- `time.Now()` разрешён в оболочке для записи момента сохранения или стартового seed, но не для игрового выбора после инициализации.
- Нельзя опираться на итерацию Go map для определения случайных исходов.
- В журнал команд записывать игровой день, тип, payload и порядковый номер; полезно для воспроизведения и баг-репортов.

## 4. Время и скорость

- Внутренний тик = **1 игровой день**. Проекты задаются в игровых днях, не в «кликах».
- `x1`, `x2`, `x3`, `x4`, `x8`, `x12` — множители относительно базового значения «игровые дни/секунду». База настраивается по тестам UX.
- Если критическое событие требует решения, игровой цикл ставится на паузу **до следующего Step**, не отменяя завершившиеся изменения этого дня.
- Временная пауза пользователя независима от системной паузы; пока есть критическое решение, попытка возобновления не снимает блокировку.
- При временных тормозах UI ограничить число шагов за кадр/интервал и корректно догонять без потери событий, либо явным ограничением backlog.

## 5. Население и пробуждение

- В первые дни население = 1, новые жители только из пригодных статуй; рождаемости нет.
- Для ранних жителей генерировать краткие индивидуальные записи; позже большинство NPC агрегируется в когорты (обобщённые компетенции), но исторически значимых жителей сохранять индивидуально.
- Модель группы должна уметь: работать, поддерживать производство, участвовать в исследованиях, влиять на культуру, стареть и умирать по агрегированным правилам.
- Пробуждение N — **атомарная проверяемая команда**: N>0; достаточно доз сока; N пригодных доступных статуй; достаточно доступной инфраструктуры (если введена как ограничение); изъять N доз и N статуй, создать N живых людей, сформировать сообщения.
- Автопробуждение — долгосрочная политика с условиями, не отдельная команда каждый тик.
- Редкость навыков — взвешенная генерация по прежней местности и общим биографиям; не гарантировать конкретного гения после фиксированного количества пробуждений.
- Уязвимость ранней общины высока, но эффект профессии зависит от оборудования: врач не лечит «современной больницей» без доступной медицины.

## 6. Сок и хранилища

- Каждое найденное и обслуживаемое дерево добавляет фиксированную величину `juicePerDay` (при желании в дробном внутреннем представлении) к резервуару.
- Формула концептуально: `stored = min(capacity, stored + sum(activeTreeRates) * deltaDays)`; переполнение теряется. **Дерево не имеет внутреннего счётчика накопления.**
- Если ранние удалённые деревья требуют наладить доступ — это разовое условие доступности/логистики, а не постоянные ручные экспедиции.
- Хранилища повышают `capacity` на уровне технологий/проектов. Не меняют `juicePerDay`.
- Если производство дробное, использовать безопасные фиксированные единицы или согласованную точность без дрейфа и отрицательных остатков.

## 7. Обобщённые ресурсы

- Еда: объём запаса/период обеспечения, потребление зависит от числа людей, производство — от занятости и технологического уровня.
- Рабочая сила: **потенциал**, не хранимый запас; ограничивает одновременно исполняемые работы.
- Производственные возможности: уровень/потенциал, отражающий оборудование и общественные возможности; не «стальной слиток».
- Благополучие: агрегат состояния; влияет на процессы и события, но не заменяет все социальные причины.
- Отдельный количественный ресурс — сок. Для микро-игры не нужны отдельные железо/медь/уголь/электроэнергия и сложная торговля.
- Отрицательное продовольствие и другие невозможные значения запрещены; дефицит выражается отдельным состоянием (`shortage`, последствия, смертность и т. д.).

## 8. Технологии: два уровня

У каждой технологии:
- `theory`: исследовательский прогресс/усвоение знаний (может накапливаться до практической реализации).
- `practical`: освоена и используется только при соблюдении критических зависимостей/производственных условий.
- `dependencies`: какие практические возможности и теории нужны, **не** «не ранее года N».
- `baseEffort`, `productionThreshold`, `branch`, `insightTags`, `effects` — конфигурируемые.
- `knowledgeRate`: исследовательские усилия, компетенции людей, подготовка, приоритеты, институты и озарения; присутствуют убывающая отдача и ограничение производством.
- Озрения могут возникать от NPC/находок/экспериментов, складываются с потолком и убывающей отдачей; книга переводит часть личного бонуса в сохраняемый общественный.
- Умер специалист: убрать его личный вклад; ранее *освоенную* технологию не удалять. Недостаток кадров может снизить эффективность производства.
- Для каждого техноузла должна существовать достижимая цепочка без обязательного редкого NPC. Предусмотреть offline-validator DAG, достижимости и отсутствия циклов.

## 9. Культура и общество

- `institutionCapabilities`: открытые возможности вроде «школа», «совет», «академия».
- `activeInstitutions`: реально организованные учреждения/нормы с устойчивым эффектом.
- `tendencies`: органические социальные состояния (например, тяга к научному познанию/совместной жизни/почитанию основателя). Они не обязаны быть видимыми числовыми шкалами.
- `processes`: длительные изменения культуры с зависимостью от событий и решений.
- Девиантное поведение: полезная инициатива, нейтральное отклонение, конфликт; не сводить к одной шкале «авторитет».
- Нужны базовые правила автономности: без новых команд цивилизация выполняет политики и развивается, даже если это отличается от плана игрока.

## 10. События и решения

Для каждого события: `id`, `priority`, `scope`, `conditions`, `weight`, `cooldown`, `effects`, `presentation`, `decisionPolicy`.
- `info`: преобразуется в сообщение, симуляция идёт дальше.
- `optional`: имеет действие по умолчанию и срок или режим делегирования; не блокирует надолго игру.
- `critical`: создаёт ровно одно обязательное ожидаемое решение, ставит системную паузу.
- Активный процесс имеет ID, стадии, локальные параметры, участников и условия выхода. «Засуха» — один процесс, а не новая засуха каждый день.
- События могут ссылаться на сохранённую историю: ID NPC, поселения, названия, дату открытия и т. п.
- Предотвращать взрыв событий: cooldown, исключение несовместимых процессов, ограничение повторов одинакового типа, сводки при высокой активности.
- Сообщения не обязаны приходить каждый день; атмосферных должно быть много, но решение от игрока требуется сравнительно редко.
- Важно: случайные события не должны мгновенно убивать игрока без какого-либо контекста и возможности снизить риск; необходимость «справедливости» проверяется массовыми тестами.

## 11. Смерть и финал

- Возраст игрока увеличивается в игровых днях от 20 лет (время окаменения не считается).
- Вероятности заболевания/старения/травмы зависят от возраста, рисков и условий, без жёсткого лимита продолжительности жизни.
- Риск-профили опасных действий должны сообщаться игроку заранее хотя бы качественно.
- Гибель — `gameOver`, отмена дальнейших тиков, неизменяемая итоговая сводка.
- Эпилог — детерминированный текст по реальным данным и истории партии, не симуляция после смерти.

## 12. Инварианты (обязательные для тестов)

1. `population >= 0`, `0 <= juice <= capacity`, `capacity >= 0`, пригодных статуй не бывает отрицательное число.
2. Пробуждено людей ≤ число когда-либо доступных пригодных статуй, учтено изъятие сока.
3. Уровни характеристик в `[0,10]`.
4. Смерть героя завершает дальнейшее изменение состояния.
5. Доступная практика не существует без необходимых зависимостей; теория может опережать практику.
6. Без новых распоряжений процессы продвигаются автоматически.
7. Скорость/пауза меняют лишь wall-clock-проигрывание, а не исход для заданной последовательности игровых тиков и команд.
8. Никакие находки не создают скрытых «складов железа».
9. Событие, помеченное критическим, блокирует дальнейшие шаги до решения.
10. Повторный запуск с одинаковыми seed и журналом команд даёт идентичный результат.
