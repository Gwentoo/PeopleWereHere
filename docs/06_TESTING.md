# 06 — Тестирование, воспроизводимость, баланс

## 1. Что именно тестируем

Не только «не падает», но и **не превращается в бесконечный гринд**. Главная цель — за ~50–60 минут реального времени показывать насыщенную, различающуюся историю, в которой некоторые партии заканчиваются раньше и не гарантируют технологии до космоса.

## 2. Минимальная инженерная проверка каждой стадии

- `go test ./...` — все тесты пройдены.
- `go vet ./...` — нет новых критических проблем.
- `go test -race ./...` — когда есть goroutine/HTTP и поддерживается средой.
- `npm run build` в `web/` — TS/frontend собирается.
- `go run ./cmd/server` — локальный браузерный сервер стартует (после этапа интеграции).
- Мануально: начать партию, продвинуть время, выполнить действие, прочитать событие, поставить паузу.
- Перезапуск браузера/сервера в момент важного события не должен терять решение (после этапа сохранений).

## 3. Unit / property tests для ядра

- Неотрицательные запасы и население, `storedJuice <= capacity`, возраст растёт, характеристики в диапазоне.
- Нельзя пробудить больше людей, чем пригодных статуй или доз сока.
- При заполненном хранилище сок не увеличивается, при доступной ёмкости увеличивается **фиксированной скоростью дерева**.
- Увеличение научных знаний не ускоряет производство конкретного дерева.
- События с невозможными условиями не генерируются; соответствующие cooldown действуют.
- Нельзя открыть практическую технологию без необходимых условий; **теория может опережать производство**.
- Утрата специалиста снижает только его персональный вклад, книги и обучение сохраняют долю; освоенная технология не удаляется.
- Критическое событие ставит движок на паузу до корректного `resolve_event`.
- При гибели героя дальнейшие тики не изменяют игровой мир.
- При одинаковом seed, правилах и одинаковых командах на одинаковых игровых днях результаты полностью одинаковые.
- Запуск с иной скоростью воспроизведения не меняет результат **по игровому времени**, если команды совпадают.
- После сохранения/загрузки и продолжения результаты совпадают с непрерывной партией; RNG state сохранён.

## 4. Headless-симулятор

Целевая команда после реализации:

```powershell
go run ./cmd/simrunner --runs 10000 --seed-start 1 --policy balanced --output results/balanced.jsonl
```

- Без UI, без HTTP, без `sleep`; не моделировать реальную минуту ожидания как игровое время.
- Один сценарий = `seed + стартовые условия + стратегия автодействий`.
- Потребуются несколько политик автоигрока:
  - `balanced`: разумные приоритеты еды/науки/поиска и ответы на кризисы.
  - `science`: научное развитие в ущерб второстепенным целям.
  - `culture`: культурные и общественные приоритеты.
  - `passive`: не вмешиваться, кроме обязательных минимальных решений.
  - `random`: допустимые случайные действия (воспроизводимые).
- Для долгой/редкой партии добавить конфигурируемую **защиту симулятора** `maxSimulatedDays`: остановить headless с пометкой `censored`, не считать это смертью героя. В обычной игре такого искусственного конца нет.

```json
{

  "policy": "balanced",
  "rulesVersion": "dev-1",
  "outcome": "player_death",
  "censored": false,
  "simulatedDays": 18750,
  "playerDeathAgeYears": 71.3,
  "causeOfDeath": "age_related",
  "peakPopulation": 2200,
  "finalPopulation": 2040,
  "treesDiscovered": 12,
  "revivedTotal": 2500,
  "technologiesKnown": 26,
  "technologiesPractical": 22,
  "firstDiscoveryDay": { "basic_metal": 145, "generators": 3210 },
  "criticalDecisions": 6,
  "infoMessages": 180,
  "meaningfulNPCs": 8

```

Все числа **примерные**, не целевой итог/норма.

Писать в `JSONL` или CSV. Допускается параллельно выполнять независимые партии, но каждая партия внутри должна быть детерминированна.

## 6. Аналитика Python

Скрипт `tools/analysis/analyze.py` должен:

- Прочитать результаты из JSONL, посчитать распределения и квантили.
- Построить: возраст смерти, финальное население, время достижения ключевых технологий, долю партий по максимальной практической технологии, частоту критических выборов и сообщений.
- Показать долю `censored` партий отдельно от смертей (важно: не подменять смерть искусственной отсечкой теста).
- Сравнивать минимум две автополитики и делать краткий Markdown-отчёт; никаких красивых дашбордов на старте.
- Выводить seed самых странных партий для детального воспроизведения.

## 7. Игровые вопросы к балансировке

1. Часто ли герой умирает в первые игровые дни без возможности повлиять?
2. Бывает ли период из десятков тиков, когда не происходит ничего интересного и ничто не меняется?
3. Есть ли партии, где люди слишком быстро заканчиваются, несмотря на пригодные статуи/сок?
4. Можно ли достичь обработки металлов за месяцы при удачных условиях? (возможно — **не обязательно** в каждой партии).
5. Нет ли жёстких пробок по годам при наличии знаний и производства?
6. Есть ли редкие, но не невозможные прорывы до поздней технологии?
7. Не является ли научная стратегия единственной выигрышной по любому разумному показателю?
8. Могут ли жители развиваться без приказов игрока?
9. Не превращается ли массовое пробуждение в 100 окон, требующих подтверждения?
10. Не создаётся ли больше обязательных решений, чем комфортно за час?
11. Сообщений достаточно для погружения, но нет бессмысленного дублирования?
12. Не рассинхронизируются ли отметки карты, история и счётчики?

## 8. Реальное время партии

Headless-прогоны **не способны самостоятельно измерить реальное время, которое живой игрок тратит на чтение и решения**. Для этого нужны ручные playtests. Замерять отдельно:
- реальное время от «Начать» до финала;
- сколько из этого времени игрок читал/выбирал/ждал;
- число ручных кликов и обязательных диалогов;
- моменты скуки и перегруза;
- насколько быстро игра начинает автоматизироваться.

Не пытаться автоматически подогнать каждую партию к ровно 60 минутам; цель — широкий комфортный диапазон и отсутствие бесполезного ожидания.

## 9. Баг-репорт и регрессии

Шаблон: версия кода и контента, seed, стартовые параметры, запись команд с тиками, ожидаемое/фактическое состояние, стек/логи. Любую найденную комбинацию, ломающую инварианты, превращать в регрессионный тест.
