# 04 — Архитектура локального приложения

## 1. Целевой стек

- **Go**: внутренний симулятор, локальный HTTP API, запуск массовых прогонов.
- **React + TypeScript + Vite**: интерфейс игры в браузере.
- **SQLite**: локальные сохранения и метаданные партий (подключается позже, когда core стабилен).
- **Python + pandas/matplotlib**: исключительно офлайн-обработка статистики после массовых прогонов (не часть runtime игры).
- На первоначальном этапе можно не использовать сторонние Go-веб-фреймворки; `net/http` достаточно.
- Без Docker в обязательном сценарии; никаких cloud-сервисов, регистраций, платежей, API-ключей и реальной многопользовательской инфраструктуры.

## 2. Как запускается игра

- **Dev:** в GoLand из терминала запуск Go-сервера: `go run ./cmd/server`, далее `npm install`/`npm run dev` в папке `web`; Vite проксирует `/api` на локальный Go-сервер.
- **Локальный запуск после сборки:** `npm run build` создаёт статические файлы, Go-сервер может отдавать их на `http://127.0.0.1:8080` (или другом явно сконфигурированном порту).
- **Headless:** `go run ./cmd/simrunner --runs 1000 --seed-start 1 --output results.jsonl` (целевая команда для реализации, не рабочая сейчас).
- В dev-режиме допускаются два локальных процесса (Go + Vite); это не два отдельных backend-сервиса.
- Ограничить прослушивание адресом `127.0.0.1`, не `0.0.0.0`. Предусмотреть CORS/dev-proxy, без доступа из внешней сети.

## 4. Границы ответственности

- **Core:** полностью контролирует правила, вероятность событий, состояния и консистентность. Не знает об HTTP, UI, SQLite, таймерах wall-clock.
- **Content:** определяет доступные технологии, события, тексты, шаблоны, конфиг баланса. Загружается и валидируется перед стартом.
- **Transport/API:** принимает команды от одного браузера, вызывает core, отправляет снимки и новые сообщения. Не рассчитывает успех действий.
- **Persistence:** сериализует/восстанавливает state, RNG, версии контента и журнал решений; не меняет правила.
- **UI:** отображает состояние и намерения игрока, группирует кнопки, не вычисляет скрытые вероятности.
- **Simrunner:** вызывает core напрямую без API/UI, применяет одну из явно описанных стратегий автоигрока.

## 5. Командная модель

Пользовательские действия не изменяют состояние напрямую: API вызывает `ApplyCommand`.

Команды примерного вида:

```json
{
  "type": "revive",
  "payload": { "count": 3 }
}
```

Типы: `start_task`, `revive`, `set_research_priority`, `set_policy`, `resolve_event`, `cancel_task`, `choose_action` (точный список формируется по этапам).

Каждая команда проверяет контекст, ограничения, возможные ресурсы, статус паузы/конца игры. Ответ явно сообщает успех или **код причины** отказа (например `insufficient_juice`), а не молча ничего не делает.

Клиент не вправе менять произвольный JSON `GameState`. Разделить `State` внутри Go и публичный `GameSnapshot` без скрытых значений.

## 6. Локальный HTTP API (целевые контракты)

| Метод/URL | Назначение |
|---|---|
| `POST /api/games` | создать новую партию с настройками и seed |
| `GET /api/game` | снимок активной партии + актуальные команды/возможности |
| `POST /api/game/commands` | выполнить команду игрока, вернуть результат |
| `POST /api/game/control` | пауза/скорость (элементы оболочки, не командная история игры) |
| `GET /api/game/events` | SSE поток сообщений/уведомлений/версий снимка |
| `GET /api/game/history?cursor=...` | страничная история сообщений |
| `POST /api/game/save` | сохранить слот |
| `GET /api/saves` | перечислить локальные сохранения |
| `POST /api/saves/{id}/load` | загрузить слот |
| `GET /api/game/finale` | итог после смерти |
| `GET /api/health` | проверка живости локального сервера |

Нет необходимости создавать все endpoint сразу. При внедрении сначала только `games`, `game`, `commands`, `control`, `events`, `health`. Позже — история/сохранения/финал.

### SSE

- Использовать SSE для уведомлений и сообщения о новой версии снимка. Лента сообщений должна иметь **монотонные event ID**.
- При переподключении клиента не запускать новую партию и не терять важные сообщения: клиент может заново загрузить snapshot и history, либо передать last event ID.
- Не пытаться передавать огромную копию полной карты каждый день; можно отправлять изменения или уведомление «snapshot updated».
- Для первого прототипа допустимо простое периодическое получение snapshot, если SSE задерживает разработку; затем заменить на SSE.

## 7. Реальное время и конкурентность

- **Одна активная партия**, её core меняется последовательно в одном контролируемом цикле.
- Нельзя выполнять `Step` конкурентно с `ApplyCommand`: использовать очередь событий/команд либо блокировку вокруг изменения state.
- При остановке HTTP соединения игровое время не обязано продолжать идти в фоне. Это **локальная игра**, сервер работает только пока запущен.
- При уходе на другую вкладку можно автоматически приостанавливать симуляцию или продолжать — зафиксировать UX-решение, но не зависеть от таймера вкладки.
- Важные решения не пропускать при ускорении.

## 8. Сохранения

- На первом этапе достаточно **in-memory**; после стабилизации — SQLite или атомарные файловые snapshot как промежуточный шаг.
- Для SQLite: `saves` (ID, имя, мета, version, saved_at, serialized_state), возможно `save_events` для истории. На малых объёмах можно хранить JSON blob, не нормализовывать весь игровой мир в 30 SQL-таблиц.
- Сохранять: полный state, seed, позицию RNG, внутренний день, журнал команд, актуальные важные события и их решения, контент-версию. Нельзя потерять ожидающий критический выбор.
- Проверять совместимость версии. Если версия сохранения неизвестна — вывести понятную ошибку, а не повреждать данные.
- Для локального проекта допустим один автосейв и несколько ручных слотов, без базы аккаунтов.

## 9. Наблюдаемость

- Логи разработчика отдельно от сообщений игрока: тайминги тиков, RNG debug seed, частоты событий, ошибки валидации и обработчики HTTP.
- По желанию `debug` endpoint **только локально** (в dev-сборке) с агрегированными скрытыми параметрами. Никогда не показывать скрытые параметры игроку как подсказки.
- В случае ошибки выводить контекст: seed, tick, версия контента, последняя команда/событие.

## 10. Качество и зависимости

- `go test ./...`, `go vet ./...` по мере появления кода; `npm run build`; форматирование и линтеры без чрезмерной настройки.
- Не тянуть тяжёлые фреймворки ради пяти обработчиков.
- Параллелизм нужен скорее **между headless-партиями**, чем внутри одной партии.
- Не подменять core UI-моками на финальных этапах: моки допустимы только для прототипирования интерфейса.
