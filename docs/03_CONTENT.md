# 03 — Контент: технологии, культура, NPC, события

> Это **начальный контент-план**, не окончательный исторический учебник. Перечисленные названия и зависимости можно редактировать в процессе балансировки. Не вводить обязательное требование пройти историческую последовательность эпох.

## 1. Общие правила контентных файлов

- Контент версионируется и загружается из файлов `content/*.json` (при желании разделить по сущностям). Каждый объект имеет устойчивый `id`, отображаемый текст на русском и явные условия.
- При запуске валидировать: дубли ID, неправильные ссылки, циклы зависимостей, отсутствие эффектов/текста, невозможные требования.
- Обычное событие представлено **данными**: шаблон, условия, веса, эффекты, cooldown. Комплексные сценарии реализуются типизированными правилами движка, а не произвольным исполняемым Go-кодом в JSON.
- Не дублировать случайную игровую логику в UI. Клиент отображает события/действия, полученные из ядра.
- Сначала добавить **небольшой полный вертикальный набор** (по 3–5 технологий/несколько событий), затем постепенно расширить до плана ниже.

### У каждой технологии должны быть

- Название, описание 1–2 предложения; направление; практические зависимости; необходимый порог производственного потенциала.
- Сколько **усилий на реализацию** требуется (пилотное число из конфига), сколько теоретического прогресса набрано.
- Источники и теги озарения, эффекты (например, открыть дальнее плавание, повышение вместимости сока, улучшение обеспечения).
- Подсказка пользователю «что мешает» без раскрытия закрытых сведений о мире.
- Пример: `generators` известна в теории, прогресс 90%, но производство недостаточно; персонажи могут продолжать готовить материалы и теорию.

## 3. Культура: «возможности + происходящее само»

### Возможности общественных институтов

| ID | Возможность | Возможный источник появления |
|---|---|---|
| `division_of_labor` | Разделение обязанностей | рост общины |
| `council` | Совет жителей | общественная организация |
| `written_rules` | Зафиксированные общие правила | письменность, культура |
| `school` | Образовательное сообщество | обучение, наличие людей |
| `archive` | Хранилище знаний | записи и материалы |
| `academy` | Научная организация | школа, исследовательские успехи |
| `local_governance` | Самоуправление поселений | несколько поселений |
| `central_governance` | Централизованная координация | масштаб общества |
| `cultural_institutions` | Учреждения культуры | устойчивые сообщества |
| `public_media` | Массовая коммуникация | связь/печать и общественные инициативы |

Эти институты — **возможности**, не обязательное дерево, где за очки покупаются «идеологии».

### Формирующиеся черты общества

- Почитание основателя, тяга к исследованиям, традиция взаимопомощи, автономность поселений, интерес к искусству, религиозные движения, централизованность, образовательные традиции.
- Возникают постепенно от решений, событий, действий важных NPC и накопленной истории.
- Могут сосуществовать, меняться и конфликтовать; не делить культуры на «хорошие» и «плохие».
- Некоторые состояния скрыты, игрок видит словесные тенденции: «растёт поддержка независимых исследователей», а не обязательно `религиозность: 63`.

## 4. NPC: широкие категории компетенций

- Четыре–шесть **обобщённых направлений знаний**, но не один уникальный слот на каждую технику.
- Пример личных черт: любопытство, инициативность, готовность сотрудничать, самостоятельность, склонность к спорам; лучше 2–3 важных признака на персонажа, чем 20 числовых шкал.
- У именованных NPC хранить: ID, имя, возраст, широкие компетенции, черты, отношение к ключевым проектам/общественным группам, достижения, ссылки на созданные книги/учреждения.
- Имена и черты должны оставаться **постоянными после сохранения/загрузки**.
- В первых пробуждениях показывать по короткому описанию на каждого; в группе N=30 — агрегированную статистику и отдельное упоминание только выделившихся людей.
- Не закреплять «врач спасает всех» или «физик сразу строит реактор».

## 6. Длительные процессы

- Сущность процесса: `processID`, `type`, `startedAtDay`, `severity`, `state`, `participants`, `cooldown/lastStageAt`.
- Примеры: засуха, затяжной конфликт, распространение нового движения, программа обучения, строительство крупного проекта.
- Каждый процесс может повышать/снижать вероятность следующих событий, закончиться сам, ослабнуть от технологий или решений игрока.
- Исключение: нельзя одновременно запускать десять независимых одинаковых засух в одном районе.

## 7. Формат описания событий (иллюстрация)

```json
{
  "id": "unknown_ore",
  "version": 1,
  "category": "exploration",
  "severity": "info",
  "conditions": [
    { "type": "region_explored_recently" },
    { "type": "not_seen", "eventId": "unknown_ore" }
  ],
  "weight": 10,
  "cooldownDays": 120,
  "messageKey": "ore_unknown_found",
  "effects": [
    { "type": "discover_landmark", "kind": "unidentified_ore" }
  ]
}
```

Схема **примерная**, её нужно описать типами и валидировать. Не разрешать произвольные поля в JSON без обработки; для текста шаблонов `{{settlementName}}`, `{{npcName}}` и т. п. выполнять безопасную подстановку по whitelist.

## 8. Начальные мини-сценарии для демонстрации

1. **Одна жизнь:** старт, вода, простейший инструмент, находка статуй, первые пробуждённые.
2. **Неизвестная руда:** событие добавляет метку; позже знания опознают минерал; открывается озарение обработки металлов и меняется подпись.
3. **Утрата специалиста:** важный NPC умирает; без книги исчезает часть бонуса, с книгой часть остаётся.
4. **Самостоятельное общество:** при 50+ жителей появляется независимая инициатива, игрок может вмешаться, но не обязан.
5. **Социальное движение:** общественное событие запускает длительный процесс, исход зависит от культуры и решений.

## 9. Качество текста

- Тексты на русском, не одинаково официозные, компактные; никаких «каждый год вы обнаружили новый камень».
- Исторические имена/названия связывать со stable ID, не генерировать «Алексей» на каждом шаге без объекта.
- Небольшие атмосферные сообщения допустимы часто, но решения не чаще, чем позволяет интересный игровой процесс.
- Не использовать внешнюю LLM для генерации реплик: сохранения и одинаковые seed должны воспроизводиться.
